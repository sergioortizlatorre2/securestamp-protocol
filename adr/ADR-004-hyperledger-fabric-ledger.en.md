# ADR-004: Hyperledger Fabric as the immutable ledger for the SecureStamp protocol

## Status
Accepted — 2026-05-24

## Context

The SecureStamp protocol requires a shared ledger among the nodes of the federated network to immutably record:
- Stamp issuances (StampIssuance)
- Revocations (StampRevocation)
- Score changes with evidence (ScoreChange)

The ledger must be publicly auditable but writable only by foundation-approved nodes. Recorded events are the **canonical state** of the protocol: any dispute about whether a stamp was issued, when, and by whom is resolved against the ledger.

Options evaluated:

| Option | Reason for rejection |
|---|---|
| **Ethereum / Polygon (public blockchain)** | Unacceptable confirmation latency (>2s) for a real-time email protocol. Unpredictable gas costs. Unwanted public governance: anyone could write. |
| **Hyperledger Besu (private Ethereum)** | EVM-compatible but inherits the complexity of the accounts model and Solidity tooling. The federated network does not need EVM-compatible contracts. |
| **Custom append-only chain** | Reinventing consensus, CA management, and gossip protocol would be unmanageable scope and an attack surface without external auditing. |
| **PostgreSQL append-only (insert-only tables)** | Not distributed by nature. A malicious node can alter its local copy. Does not provide cryptographic proof of non-alteration for third parties. |
| **Hyperledger Fabric** | Permissioned blockchain, integrated CA, chaincode in Go/Node, configurable single channel, no token/gas, mature Raft consensus, adopted by the Linux Foundation. |

## Decision

Use **Hyperledger Fabric** as the distributed and immutable ledger for all SecureStamp protocol events that require inter-node consensus.

### Components and roles

**Certificate Authority (CA)**
- Issued and operated by the SecureStamp Foundation.
- Signs the identity certificates of each Peer node before admission to the channel.
- Without a valid CA certificate, a node cannot read or write to the ledger.
- Allows revocation of compromised nodes via CRL.

**Orderer (Raft)**
- Serializes transactions and produces blocks.
- MVP: a single orderer operated by the foundation (acceptable for the initial phase).
- Production: minimum 3 orderers in Raft for fault tolerance (F = 1 with 3 nodes, F = 2 with 5).
- Does not store world state; only orders and distributes blocks.

**Peer nodes**
- Each approved node in the federated network operates a Peer.
- Maintains a local copy of the ledger and world state (LevelDB or CouchDB).
- Executes chaincode to validate transactions before endorsing.
- Endorsement policy: `AND('Foundation.member', 'Org1.peer')` in MVP, expandable to majority in production.

**Chaincode (smart contracts)**
- Written in Go, deployed in the `securestamp-main` channel.
- Three assets: `StampIssuance`, `StampRevocation`, `ScoreChange`.
- All writes go through chaincode — there is no direct ledger access from nodes.
- Chaincode validates that the emitter has the correct role before creating the asset.

### Events recorded in the ledger

```
StampIssuance {
  stampId:    string   // UUID v4, generated by the issuing node
  orgId:      string   // Organization ID registered with the foundation
  domain:     string   // normalized domain (lowercase, no trailing dot)
  score:      uint8    // 0–100
  signals:    string   // serialized JSON: { spf, dkim, dmarc, ... }
  timestamp:  int64    // Unix epoch ms
  issuedBy:   string   // fingerprint of the issuing node's certificate
}

StampRevocation {
  stampId:    string   // reference to StampIssuance.stampId
  reason:     string   // enum: PHISHING_DETECTED | ORG_REQUEST | POLICY_VIOLATION | NODE_COMPROMISE
  revokedBy:  string   // fingerprint of the revoking node's certificate
  timestamp:  int64
}

ScoreChange {
  domain:     string
  oldScore:   uint8
  newScore:   uint8
  reason:     string   // enum: DMARC_ADDED | PHISHING_CAMPAIGN | TYPOSQUATTING_CLUSTER | MANUAL_REVIEW
  evidence:   string   // JSON array of signals justifying the change
  timestamp:  int64
}
```

### MVP setup

The MVP operates with a minimal topology for development and staging:

```
1 CA (foundation)
1 Orderer (Raft, single node)
1 Peer (foundation, org = Foundation)
1 Channel: securestamp-main
Chaincode: securestamp-core v0.1 (Go)
```

This configuration is not fault-tolerant but is functional, auditably correct (the ledger remains immutable and cryptographically signed), and sufficient to integrate the first approved external node.

Infrastructure: Docker Compose for local development, Kubernetes (EKS) for staging/production.

### Scaling to production

- Add orderers up to a minimum of 3 (Raft majority).
- Each new foundation-approved organization adds its Peer to the channel.
- Endorsement policy migrates to `MAJORITY` of endorsing peers.
- CouchDB as state database for complex queries on the world state (e.g., all active stamps for a domain).

## Consequences

**Positive:**
- Immutable and cryptographically auditable ledger without a central custodian.
- Integrated CA allows revoking compromised nodes without restructuring the network.
- No token, no gas: the protocol's economics are independent of cryptocurrencies.
- Chaincode in Go with standard testing.
- Permissioned by design: exactly the model needed for a federated network with approved nodes.
- Adopted by the Linux Foundation — institutional credibility for the open protocol.

**Negative:**
- Operationally complex: CA, orderers, peers, channel config, and chaincode are components requiring dedicated DevOps.
- The single-orderer MVP is an operational single point of failure (not of integrity — the signed ledger remains auditable even if the orderer goes down).
- High learning curve for developers unfamiliar with Fabric.
- Tooling (peer CLI, configtx) is not as ergonomic as other solutions.
- Confirmation latency ~500ms–2s depending on the orderer's batch timeout — acceptable for event recording, not for real-time verification (verification uses each node's local DB, not the ledger directly).

## Alternatives considered

- **Ethereum / Polygon**: rejected for economic and governance reasons.
- **Hyperledger Besu**: technically viable but EVM tooling unnecessarily complex for this use case.
- **Custom append-only chain**: out of scope and without external auditing.
- **PostgreSQL append-only**: not distributed, does not provide cryptographic proof for third-party auditors.
